# Next Python SFT dataset: research and proposed release plan

Researched November 11, 2026. This is a recommendation, not a selected recipe, prepared dataset, measured optimum, or promise of benchmark performance. No training, installation, bulk download, paid generation, or hardware rental was performed. Web inspection covered primary papers, original repositories, dataset cards and small public viewer previews; it did not audit entire datasets. Exact post-filter Python counts and Qwen-token length distributions remain unmeasured.

## Decision in plain terms

**Latest planning revision, November 11:** the user challenged another ~100K main run after S1's ~117K and wants more, stronger examples. The assistant revised the working recommendation to **300K accepted distinct Python examples, with possible expansion to 500K**. This is an unselected experiment target, not a new research finding or measured optimum; no new evidence establishes 300K as better than 100K for this model. The earlier 100K mixture and scaling examples below remain optional diagnostic templates, not the intended main-run size. Do not require another 100K run before preparing the larger candidate.

Use **OpenCodeInstruct as the main candidate pool**, execution-filtered StarCoder2 instruction data as a complementary source, a smaller cleaned educational subset, and a modest short instruction-following component. Compare an optional KodCode substitution separately if its noncommercial license suits the intended use. Do not mechanically triple the earlier quotas: source yields and distinct problem families must be audited first.

Both the earlier 200K–500K suggestion and the revised 300K target are planning proposals. Neither should be called the optimal range. There is no controlled evidence establishing an optimal row count for this exact 0.5B checkpoint, Python-only scope, curation procedure and token budget. A million rows remains an expansion option after learning whether additional clean, distinct tasks help.

S1 already used roughly 117K short examples according to historical observations. The proposed gain is broader, better checked supervision and a better experiment, not merely a bigger number. Do not claim that replacing data alone will fix S1: recovery lineage, tokenizer warning, training settings, prompt format and generation limits still need consideration.

## What the strongest reference actually supports

[Qwen2.5-xCoder, ACL 2025](https://aclanthology.org/2025.acl-long.642.pdf), Table 1, reports 0.5B SFT **69.5 HE / 66.5 HE+**, and DPO **72.6 / 67.1**, with greedy pass@1. Section 3.3 describes ~97.3K multilingual SFT instructions and ~133K DPO samples; section 3.1 instead says ~95K. The paper identifies Qwen2.5-Coder foundation models as its starting family, but gives no pinned 0.5B checkpoint revision or complete size-specific reproduction manifest. Its data-size analysis is not a controlled 0.5B Python-only optimum. I could not locate an official downloadable X-INSTRUCT release or xCoder checkpoint in the paper links and targeted release searches; availability remains unverified. Do not substitute similarly named XCoder-80K.

Our S1's screenshot-evidenced 30.5 HE / 28.0 HE+ is under the saved project protocol, not a reproduction of that paper. For this SFT project the SFT row is the relevant aspirational reference; DPO adds a separate training stage. No proposed mixture guarantees either score.

[OpenCodeInstruct](https://arxiv.org/html/2504.04030v1) provides stronger scaling evidence for larger models: section 4.2 studies 7B/8B models, with gains through the full 5M samples. Table 4's 500K, 7B comparison finds perfect judge-score selection stronger than merely selecting generated-test passes. This supports evaluating both signals, not assuming test passage proves correctness or extrapolating its optimum to 0.5B. Its response teacher is Qwen2.5-Coder-32B-Instruct; related ablations use other Qwen teachers. Natural-language task diversity is another useful lesson.

[Wang et al.'s XCoder study](https://arxiv.org/html/2409.03810v1), a different project, reports on Llama3-8B that selected 80K examples match random 320K on its LiveCodeBench comparison (Table 7). That is evidence for selection efficiency, not a promise about our model. Its leakage discussion motivates independent decontamination.

## Curation protocol before formatting

1. **Immutable provenance.** Pin actual dataset commit SHAs and configuration/split; record original ID, seed/family/source IDs, teacher identifier where supplied, original license, raw-content hash, processing version and rejection reasons. Never invent absent provenance. Keep raw and normalized fields separately. No SHAs were pinned as a selected release in this research.
2. **Scope and semantic validity.** Require a complete, unambiguous Python problem, matching signature/entry point, all imports and no unavailable context. Initially standard library and pure functions; reject repository-dependent fragments, web/API access, third-party packages, interactive input, ambiguous multiple answers, contradicted examples, empty responses and truncated code. Make a separate track for filesystem tasks if later desired.
3. **Execution evidence.** Parse the actual final assistant solution, run all associated tests in a restricted disposable container with time/memory limits, and record interpreter/container digest. Require nonempty tests, correct function invocation and genuine assertions that run. Reject unconditional-pass tests, swallowed exceptions and skipped tests. For OpenCodeInstruct begin with all recorded tests passing plus high requirement/correctness judge scores; parse JSON numerically. A strict all-5 judge threshold is an ablation, not an empirically optimal universal cutoff.
4. **Test quality.** Sample-check empty/singleton inputs, ties, negative values, Unicode, off-by-one boundaries, ordering and mutation requirements as appropriate. Use independent tests or brute-force oracles on simple finite domains; check that intentionally wrong solutions fail. Branch coverage helps find gaps but proves neither specification correctness nor test independence. Synthetics may have matching bugs in both answer and tests. If tests are newly added later, record generator/cost and don't call them independent merely because there are more of them.
5. **Deduplicate across all sources.** Hash normalized instructions, code and AST forms; use token/shingle similarity and semantic retrieval to find paraphrases and rewritten solutions. Review borderline clusters. Keep a representative or tightly cap a cluster; don't treat every shared algorithm as a duplicate. Group seed descendants, source problems, format conversions and full conversations together. Record how many unique families remain, not only rows.
6. **Decontaminate before splitting.** Exclude benchmark questions, solutions, benchmark-derived synthetic descendants and task IDs across HumanEval(+), MBPP(+), and every other evaluation suite reserved for this project. Compare instruction text and normalized solutions, combine exact/n-gram matches with semantic candidate review, and remove an affected source family when lineage supports it. Benchmark test material belongs only in the audit/grader, never model prompts, training targets or reward-development tasks. A single cosine threshold cannot certify cleanliness; record unresolved lineage and audit limitations. Existing upstream filtering does not replace this audit.
7. **Create immutable group splits.** Proposed extra 2K development and 2K untouched internal test tasks, grouped by problem/seed/near-duplicate family and balanced by source/topic. Freeze test before tuning; use development execution and instruction compliance for choices. If separate datasets are used, preserve their official test exclusion. The existing project split named `test` is validation, not this new untouched test. Do not merely move duplicate validation answers back into training as a substitute for grouped splitting.
8. **Audit manually before release.** Review a stratified 200-row sample, covering every source, long examples, difficult tasks, low-confidence tests and borderline clusters. Publish observed defect types/counts, not just a quality adjective. Recheck after repairing the selection rules. Keep a rejection ledger and a reproducible manifest.

## Length, difficulty and answer format for 0.5B

Use the **actual local Qwen tokenizer**, chat template and assistant end marker to measure prompt tokens, completion tokens and total tokens. A source viewer's string length is not a token count. Report per source: median, p90/p95, maxima, length-bucket counts, supervised-token share and fraction lost at 512/1024/2048. No such distribution was measured for the proposed mixture.

Proposed first limit: **2048 combined tokens**, subject to a short memory/numerical stability check on the chosen hardware. Preserve complete examples; route or reject overlength examples instead of truncating the answer. This relaxes S1's 512-token admission rule without turning the project into long-trace distillation. Start with about 80–90% of accepted coding rows at <=1024 combined tokens and retain a 1025–2048 tail if it supplies useful complete tasks. These percentages are pilot choices, not a discovered optimum.

Plan a **60M–100M nonpadding combined-token** target for 100K rows (600–1000 average), then replace it with measured values. Do not force the mean by padding or changing correct answers. Prompt tokens still cost compute under completion-only loss. Measure supervised completion tokens separately.

For the revised 300K planning target, that same hypothetical mean would imply 180M–300M combined tokens per epoch. This is conditional arithmetic, not a measured length distribution or training budget.

Favor concise direct solutions with sufficient specification complexity: strings, lists/dicts/sets, counting, parsing, sorting/search, numeric edge cases, recursion, basic graphs and dynamic programming. Avoid filling the corpus with both trivial near-duplicates and olympiad-only challenges. Tentative 50% basic / 40% intermediate / 10% challenging **topic/complexity** bands should be revised using development evidence; they are not teacher difficulty labels. Keep challenging but learnable problems even when a baseline cannot solve them immediately.

For code-only requests return code; for explanation/debug requests retain a short correct explanation plus code as appropriate. Do not mechanically strip all prose or add “code only” to prompts whose target is explanatory. Do not attach generation scaffolding, hidden tests, teacher judging text or R1 traces to the prompt. Retain tests/provenance outside model-visible fields. For the first release, normalize into single-turn user/assistant pairs using the established Qwen template. Check assistant masking and stopping before a run.

The 5% auxiliary slice is a hypothesis about usable instruction following, not an identity-training solution or guaranteed coding gain. Compare it with replacing those same tokens by coding tasks; evaluate prose/constraint compliance and code correctness together. A Python specialist need not learn a fabricated company/model identity.

## How to determine the useful scale without wasting a run

First measure B0 and optionally official Instruct under the saved S1 protocol; keep raw outputs, truncation counts, hashes and grader digest. Also use an appropriate completion prompt for base-model capability assessment, reported separately: the shared chat protocol alone measures an unaligned base's chat behavior. Verify S1 recovery lineage and investigate tokenizer behavior before interpreting a data experiment.

Recommend S2 from the **same original base** for the cleanest S1/S2 comparison. Continuing S1 is still an open user choice: it adds prior educational exposure and changes the question. Record actual starting checkpoint and don't compare those lineages as equal-data experiments.

For the revised main-run target, prepare the full 300K candidate first. Optional smaller subsets can measure scaling if the user wants to spend compute on that comparison. The original diagnostic design used nested, stratified **50K ⊂ 100K ⊂ 200K unique-family** selections; it can instead compare, for example, 100K versus 300K without requiring the smaller run. Preserve source/topic/length proportions and release their measured tokens. Prefer only one tested curation rule initially; vary source choice separately.

- **Practical scaling:** one epoch each at the same training settings, with the schedule defined consistently in consumed tokens. This measures more unique data **plus more compute**; label both.
- **Compute-controlled subset:** match total processed nonpadding tokens. Contrast 50K with repetition versus 100K with fewer repetitions; match length distribution, supervised-token fraction, batch tokens and learning-rate schedule as closely as possible. Repetition is part of this comparison, not a hidden control.
- **Source comparison:** at fixed row/token budget, compare the main mix with KodCode substitution (if eligible) or a cleaned educational-only control. This separates source/selection from scale better than comparing S1 against a run that also changes length, precision and optimizer.
- If resources are limited, prioritize a stable pilot and one well-audited larger candidate over an obligatory scaling sweep. Use multiple seeds for close decisions if affordable. Prefer paired task outcomes and uncertainty estimates over a one-task benchmark increase.

Use frozen development tasks for checkpoint/hyperparameter choice. HumanEval is already observed, so it cannot serve as a pristine future test; don't repeatedly optimize the recipe on its 164 tasks. Run a frozen untouched internal test only for selected candidates, and disclose any additional published benchmarks used for development. Keep exact S1-compatible benchmark settings for historical comparisons; any larger output budget is a separately named protocol applied consistently to all models.

## Compute and budget planning

No cloud rate or throughput is assumed here; the prior chat's rates and 5K/10K/20K tok/s illustrations were not measured training speed. Before a paid full run, the user should profile the actual model, precision, attention backend, length distribution, batching/packing and optimizer. Validate finite forward/backward/optimizer state and a checkpoint reload, particularly given the prior ROCm NaN incident. Don't prescribe CUDA-specific optimized kernels for the AMD machine without checking support.

After warmup, time a representative 100–200 optimizer-step pilot including several length buckets, and separately measure checkpoint/evaluation overhead and peak memory. Report processed nonpadding tokens/second and actual padded tokens/second, not generation speed or misleading resumed progress-bar iterations. If considering NVIDIA cloud, run a compatibility pilot there rather than projecting AMD speed.

For measured throughput R, N examples, mean L combined tokens and E epochs:

`training_hours = N * L * E / R / 3600`

`estimated_cost = hourly_rate * (training_hours + measured_overhead) + storage + other billed costs`

For example, 100K rows at a measured mean of 800 tokens is 80M tokens/epoch; this is arithmetic, not a measured corpus size. A 50K+100K+200K one-epoch sweep at the same mean totals 280M tokens before ablations. Repeated epochs and failed runs multiply work. Test generation/verification and synthetic teacher calls are separate costs. Recheck live instance prices and availability when choosing hardware; no rental or spend is authorized by this note.
